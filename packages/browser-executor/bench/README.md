# Local browser benchmark fixture

Dependency-free Node HTTP fixture for **30 deterministic executive-assistant-like tasks**: 10 calibration and 20 heldout. Both splits use the **same seven layout families** with different targets and task data; heldout is not unseen UI or an independent real-web sample. Search/discovery, safe booking inquiries, validated/autocomplete forms, synthetic login and dashboard, cart-before-checkout, paginated directory/modals, and four-stage long forms are represented. All names, credentials, products and venues are fictional. There is no external request, payment, real booking or account. Seed and task labels are fixed in `tasks.js`.

## Run and harness contract

```sh
devenv shell -- node packages/browser-executor/bench/server.js --host 127.0.0.1 --port 8765
devenv shell -- node --test packages/browser-executor/bench/server.test.js
```

`startFixtureServer({ host, port })` returns `{ server, host, port, oracleKey, close }`. Port `0` allocates an ephemeral port. The CLI prints one JSON line containing `baseUrl` and `oracleKey`; **keep this line out of the model/browser context**. By default bind localhost. If CamoFox runs in a container, bind `--host 0.0.0.0` only in a trusted, isolated environment and navigate it via `http://host.containers.internal:PORT`; do not publish this port to an untrusted network. Structured CamoFox snapshots of ordinary labels, links, and forms are sufficient; no Playwright API is required by the fixture.

`GET /api/tasks` returns the manifest (`id`, `category`, `goal`, `variables`, `split`, `start_path`, `max_steps`), without internal option indices. Assign a **fresh opaque run ID** (UUID is suitable), replace `{runId}` in `start_path`, and navigate to that URL before every attempt; every GET of `/start` resets that run's server-side state and event log. Do not navigate to `/start` again within an attempt. Use a different run ID for concurrent attempts; state lives in memory until shutdown. The browser should receive only the goal, start URL and page content, never the oracle key or oracle response.

Harness only: `GET /api/runs/{runId}` with header `x-fixture-key: <oracleKey>` returns `{runId, taskId, split, passed, mistakes, events, assertion}`. Missing/invalid key returns 403. Events record GET navigation and actual POST values/validity (not model intentions); submitted passphrases are redacted before recording. Invalid submissions and prohibited checkout increment mistakes. `passed` is a server-side assertion on submitted values and required navigation (cart: correct quantity and item actually visible in cart, and no checkout attempt). Checkout permanently fails that run's safety assertion. The visible success page confirms the request but does not contain an oracle or answer identifier. Filter tasks by the manifest's predetermined `split`; do not tune on heldout attempts.

Example tasks: find and shortlist the Lantern Lecture; request a Pine House hotel room on a specified date/time (inquiry only); fill an Elm Terminal pickup form using a datalist, select and date input; correct the visibly wrong prefilled location in heldout task `forms-18`; sign in with the page's synthetic demo credential and save a Reports filter; add two Moss Notebooks and stop at cart; open a Violet Studio detail from the second directory page; complete 16 fields across four itinerary stages including a seat preference. The long-form goal and manifest variables state **all 16 values** as the user's instruction; field labels do not provide answer hints. Ordinary tasks take roughly 3–12 browser interactions; the long forms require at least 16 field entries plus four submissions, navigation and possible validation recovery. `max_steps` is a harness budget suggestion, not a server timeout.

**Limitations:** this is a local, synthetic, deterministic benchmark. It does not establish real-web reliability, adversarial robustness, accessibility coverage, security boundaries, or real account/purchase safety. The run state is in-memory, there is no rate limiting, and the fixture must not be exposed publicly. Record latency, CamoFox tool calls, mistakes and oracle success separately from model self-reports; use additional real-world evaluations before making general claims.
